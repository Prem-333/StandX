# Project-wide safeguards

These requirements come from the project owner and apply to all phases.

1. Never invent real IS numbers, titles, or cross-references. Until verified metadata is available, use clearly labeled MOCK/SYNTHETIC records with identifiers such as `IS-MOCK-0001` and `"source": "synthetic"`. Keep those labels visible in every API response, demo, and screen using them. Synthetic records must never be represented as verified BIS records.
2. Treat standards full text as copyrighted, licensed content. Store and index only public metadata: number, title, scope abstract, classification, group/sub-group, cross-references, supersession chain, revision/amendment metadata, and certification flags. Full-text storage/indexing requires licensed PDFs explicitly supplied by the user. Do not download or redistribute full standard PDFs from BIS portals, even if reachable.
3. Every recommendation must cite a specific knowledge base record and its IS identifier. Evidence must support any related-standard or certification claim. Missing evidence means unknown, not false or not applicable. Disclose low confidence and abstain when evidence is insufficient.
4. Before hardcoding potentially stale facts, including dependency versions, models, endpoints, government schemes, legal/certification requirements, prices, and deadlines, announce what is being checked and why, then verify it through a live lookup. Prefer official or primary sources. Do not silently substitute remembered facts.
5. Every fact, dataset sample, or dependency version retrieved online must append an entry to `docs/SOURCES.md` containing the exact URL, fetch date, and one-line use note. Root `SOURCES.md` links to this canonical audit log. Record relevant robots/terms checks there too. Do not put secrets or access tokens in logged URLs.
6. Respect robots.txt, Terms of Use, access controls, and licensing. BIS portal access is limited to read-only, low-volume, spaced-out public metadata lookups. No bulk scraper or high-volume harvesting. Establish the applicable access rules before portal retrieval.
7. If internet access fails, tell the user immediately. Any fallback must be labeled exactly: **unverified — confirm before relying on this**.
8. Preserve the requested layout: `data/raw`, `data/processed`, `data/mock`, `kb`, `services/api`, `services/ingestion`, `services/nlp`, `frontend`, `eval`, `docs`, root `PROJECT_CONTEXT.md`, `SOURCES.md`, `README.md`, and `.env.example`.
9. Default architecture: Python 3.11 + FastAPI, PostgreSQL, local Docker Qdrant and Neo4j, local embeddings through sentence-transformers or Ollama, React + Vite, and Docker Compose for local offline runtime. Verify concrete packages, images, models, and integration details when implementing them. Document the initial provisioning needed for offline operation.
10. End every phase with a short `PROJECT_CONTEXT.md` entry, a `README.md` section, and a runnable `make phaseN-demo` target or npm/uv script. Do not describe placeholder functionality as implemented.

11. Phase 2 onward uses the owner's explicit provenance tags: `bis_public_metadata_verified` for individually checked BIS public metadata and `synthetic_seed` for synthetic seed records, with `IS-SEED-…` identifiers and visible MOCK/SYNTHETIC titles. The earlier Phase 0 `synthetic` fixture remains a separate legacy example. A verified page observation does not certify legal applicability, completeness, or latest publication status.
12. The manual Phase 2 sample is capped at 20–30 standards; the collected sample contains 20. No bulk BIS collector is authorized. Offline parsers and loaders must never initiate BIS requests.
13. Graph expansion may use only evidenced typed relationships; preserve generic references as untyped. Version resolution must follow the entire supported supersession chain and expose unknown amendment resolution.
14. Embedding and reranking inference must run locally with cached, verified model files; never call an external embedding API. Model swaps are configuration changes plus an explicit offline index rebuild. Online provisioning is a separate command; runtime must fail if required assets are missing.
